## V3-P1 — Make the real validation REPRODUCIBLE (the dominant remaining gap) **[Opus-verified]**

**Severity:** High for "done" (the code is ready; the *proof* is a one-time manual attestation).
**Spec/context:** v2-P4 "definition of done"; `artifacts/remote-validation/2026-06-04-p620-blackbird-smoke.md`.

**What's true now (good):** a genuine real run happened — handshake, agent-owned list/preview, a real Qwen launch returning `READY http://10.25.0.51:18003`, a real `vllm==0.11.2` build install/verify, a real tiny HF download/verify, and daemon-restart + disconnect/reconnect resume. The corroborating fix-commits (`tqdm` runtime dep, `ensurepip` bootstrap, restart-daemon-after-install, venv-context wrapper, launch-auth-for-health) are the signature of genuine real-world execution. **[Opus-verified — artifact read + fix-commit corroboration weighed.]**

**What's not yet true (the gap):**
- **Not reproducible / not in CI.** `tests/test_remote_workflow.py` still only content-asserts `run_remote_tests.sh` and runs it against a **fake `ssh`** stub; nothing automated touches real hardware. A future Blackbird regression would not be caught.
- **Validated near-HEAD, not at HEAD.** Real build install at `ec8f374`, Qwen smoke at `1c6c0aa` — both behind current HEAD by 10+ commits.
- **Resume/daemon-restart ran against `fake_vllm_child.py`**, not a real multi-GB model load (inode/offset values are real; the monitored process was fake).
- Single-person attestation; laptop-sleep not exercised.

**Fix direction.** Turn the one-time run into a repeatable gate: (a) a single `scripts/run_remote_tests.sh` invocation (or `make validate-remote`) that, given `USER@HOST`, *executes* one tiny real install + tiny real HF download + a short real launch smoke and **writes a fresh dated artifact**; (b) a **manual-trigger CI lane** (or a documented pre-release checklist) that runs it against a real GPU host and pins the result to the validated commit; (c) re-run the build-install + Qwen smoke **on current HEAD** and refresh the artifact; (d) ideally one resume/daemon-restart pass against a *real* (small) model, not the fake child.

**Acceptance.** A dated `artifacts/remote-validation/<date>-…md` generated by a single repeatable command at HEAD, plus a CI lane (even manual-dispatch) that executes — not greps — the real path.

## V3-P2 — Finish FlagManager editing **[Opus-verified]**

**Severity:** Medium (the one UI feature that's partial vs its spec).
**Spec:** build §9.5 — browse **+ edit + soft-validate + live preview** + persist.

**Problem.** `tui/screens/flag_manager.py` browses modeled/passthrough/unknown flags (from agent `flag_map`/`known_flags` metadata), supports reset-to-default (`d`), and persists via `update_config_flags` — but has **no `Input` widget**: you cannot type a new value for a flag, there's no soft-validation on edit, and the resolved-command preview is **static at open time**, not live.

**Fix direction.** Add inline editing (an `Input` per selected flag), run the build's `soft_validate` on edit (warn, don't block), and re-render the `build_command` preview on each change (the agent already returns the preview/metadata).

**Acceptance.** Edit a modeled flag → preview updates live + soft-validate warning on an unknown enum → save round-trips into the config's `engine`/`extra_args`; a smoke test covers it.

## V3-P3 — Decide url-source model download **[Opus-verified]**

**Severity:** Medium-Low.

**Problem.** `pin_model` accepts a `url` source (registry + TUI + CLI all wired), but `download_model` for `source == "url"` returns `feature-unavailable` (`agent/local.py:~1790`). So a url-pinned model has no fetch path.

**Fix direction (pick one, decisively):** either (a) implement a real fetch (stream-download the file as a job, scrubbed, like the HF path), or (b) declare url models **launch-time-only** (vLLM takes the URL as `--model` directly), make the TUI/CLI say so, and remove the misleading `feature-unavailable` download affordance for url entries.

**Acceptance.** Either a working url download job, or url entries clearly marked "no pre-download (resolved at launch)" with no dead download action.

## V3-P4 — Wire the controller to the new `preflight`/`restart` RPCs **[Opus-verified]**

**Severity:** Low (tidiness; functionally fine today).

**Problem.** `preflight` (returns serializable `{ok, failures}`) and `restart` (agent-side stop/wait/launch with controller-minted `new_run_id`) are implemented agent-side, dispatched in `handle()`, and capability-negotiated — but the **controller never calls them**: it still uses `prepare_launch` (preflight as a side-effect) and stop-poll-`action_load()` for restart.

**Fix direction.** Have the controller call `preflight` directly (surfacing `failures` before launch) and `restart` (atomic agent-side) where it currently composes stop+load. Optional but realizes the spec's intent and removes a controller-side poll loop.

**Acceptance.** `action_restart` issues a `restart` RPC; a pre-launch preflight call surfaces structured failures.

## V3-P5 — Minor: registry lock consistency **[Opus-verified]**

**Severity:** Low (single-agent deployment; low-probability).

`pin_model` (`model_registry.py:~119`) acquires only the **registry** lock, whereas `verify_model`/`remove_model` acquire **entry + registry** (nested). A concurrent `pin_model` + `download_hf_model` on the same entry has a small TOCTOU window. Apply the nested-lock order consistently across all entry write paths.
