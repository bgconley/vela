## Key Learnings
- Operator-stop toast immunity lives ONLY in the `current_run_id == run_id` terminal guard (app.py `_monitor_attached_run`): `_operator_signal_verbs.pop(run_id, "stop")` has a DEFAULT, so popping/clearing the verb dict does NOT suppress the announce. Any restart/stop suppression must re-point `current_run_id`, never the verb registry (established A3, commit a3493d7).

- **Project:** lab-tui
- Canonical v2 requires detached mode to survive TUI/CLI exit; supervisor must drain child pipes live and write scrubbed durable logs, sidecar, and manifest for reattach.
- Script executables launched through a shebang may briefly report `/usr/bin/env`; sidecar identity should record the actual settled process cmdline/executable before verification.
- Health probing must continue after READY; the TUI should consume loop events so health failures move to DEGRADED and later 200 responses recover to READY.
- Health checks must treat `/v1/models` connection failures like `/health` connection failures because shutdown can happen after `/health` returns 200 but before the model probe completes.
- `/health` 200 proves liveness; malformed `/v1/models` JSON should not crash the probe, and should return READY with empty models plus an invalid-JSON detail.
- `/v1/models` payload shape is advisory too; wrong JSON shapes should return READY with empty models plus an unexpected-shape detail rather than raising during model extraction.
- `/v1/models` 401 is not advisory; even if no API key is configured locally, classify it as `HF_AUTH` so remote smoke does not claim READY for an auth-blocked model endpoint.
- Health probing should preserve explicit `server.probe_host`, preserve loopback bind hosts, and otherwise probe `127.0.0.1` for non-loopback bind addresses per the canonical spec.

## Session 2026-07-12 (Phase 8 — docs golden paths) learnings

- **Key Learning (daemon-leak root cause, bug-303):** `stop_agent_daemon` (daemon.py) used to return `"stopped"` as soon as `not identity_path.exists()` in its SIGTERM wait loop — but `run_agent_daemon`'s finally unlinks the identity file as the LAST graceful-shutdown step, and the process can still be ALIVE afterwards (racy: sometimes hangs in `asyncio.run` teardown / `shutdown_default_executor` joining a lingering thread). The premature `"stopped"` SKIPPED the SIGKILL escalation, so a hung daemon was never force-killed → reparented to launchd → accumulated (reviewer saw 13 `vela-test-state-*`). conftest's session-teardown `vela agent stop` inherits this, leaking ~1 per full-suite run. FIX: gate `"stopped"` on `not _identity_matches_live_process(status)` (process actually gone — dead/zombie/replaced, since `_identity_matches_live_process` returns False for STATUS_ZOMBIE and NoSuchProcess) rather than the identity file's absence, so a laggard times out the SIGTERM window and gets SIGKILLed. The existing `test_agent_stop_escalates_when_daemon_ignores_sigterm` KEPT its identity file, so it never covered the identity-vanished-but-alive case — the regression test (`test_agent_stop_kills_daemon_that_unlinks_identity_then_lingers`) uses a helper that unlinks its OWN identity on SIGTERM then keeps running, and asserts the process is actually reaped.
- **Key Learning (diagnosing the leak):** `os.kill(pid, 0)` reports a ZOMBIE as alive (it exists in the process table until reaped), so a repro that only checks `os.kill(pid,0)` can't tell "hung live daemon" from "reaped-later zombie". Use `ps -o stat=` (`Z` = zombie) or `_identity_matches_live_process` (False for zombies) to classify. A daemon spawned via `subprocess.Popen(start_new_session=True)` whose Popen handle is GC'd becomes an unreaped zombie child until the parent (pytest) exits; only a genuinely HUNG (non-zombie) daemon reparents to launchd and accumulates across runs.
- **Key Learning (drift-proof generated docs):** `scripts/gen_tui_docs.py` walks `VelaApp.BINDINGS` + each screen's OWN `cls.__dict__.get("BINDINGS")` (never inherited) via `pkgutil.iter_modules(vela.tui.screens)` + `issubclass(obj, Screen) and obj.__module__==module.__name__`. BINDINGS entries are a MIX of plain tuples AND `textual.binding.Binding` objects (NOT a tuple subclass in 8.2.7 — `isinstance(b, tuple)` is False), so normalize both. `docs/tui.md` is committed; `test_docs.py::test_tui_doc_matches_bindings` loads the script via `importlib.util.spec_from_file_location` (scripts/ is a namespace pkg, not importable as `scripts.x`; this is the repo convention — see test_remote_workflow.py) and diffs `render_tui_docs()` against the committed file.
